# 調査系エージェントの棚卸し

`.claude/agents/*-analyzer.md` の記述が、対象リポジトリの現在の構成と乖離していないかを点検し、
必要なら更新する。**検出・分類・提示までを自動で行い、編集はユーザー承認後にのみ実施する。**

## 前提

- 実行するのは <PORTAL_REPO> リポジトリ上のメインセッション。`repo-writer` やサブエージェントには委譲しない
  （<PORTAL_REPO> 自身の `.claude/` を編集するのはメインセッションの責務のため）
- 対象リポジトリの作業ツリー・チェックアウト中のブランチには**一切触れない**。`fetch` のみ行う

## ステップ1: 対象の特定

`.claude/agents/*-analyzer.md` を列挙し、各エージェントの `PATH_FILE`（`~/.claude/` 配下の
パス設定ファイル名）と対応リポジトリを特定する。エージェント本文中の
`~/.claude/<name>-repo-path.txt` の記述から機械的に抽出できる。

## ステップ2: パス設定の健全性チェック

各 `~/.claude/*-repo-path.txt` について以下を確認する。

```bash
for f in ~/.claude/*repo*path*.txt; do
  p=$(cat "$f"); q="${p/#\~/$HOME}"
  [ -d "$q" ] && echo "OK   $(basename $f) -> $q" || echo "NG   $(basename $f) -> $p"
  [ "$p" != "$q" ] && echo "     ※チルダ形式で保存されている（要修正）"
done
```

- **チルダ形式（`~/git/...`）で保存されている**場合は不具合。シェル変数内のチルダは展開されず、
  `ls: ~/git/...: No such file or directory` で調査コマンドが必ず失敗する。絶対パスへの
  書き換えを提案する
- **未設定**の場合は不具合ではない（初回起動時にユーザーへ質問する設計）。情報として報告する

## ステップ3: 対象リポジトリの最新化

```bash
git -C "$REPO" fetch origin -q --prune
```

- `pull` / `checkout` / `merge` は行わない。以降の比較は常に `origin/<既定ブランチ>` を基準にする
- 既定ブランチは `git -C "$REPO" symbolic-ref refs/remotes/origin/HEAD` で取得する
  （リポジトリごとに既定ブランチ名が異なりうるため決め打ちしない）

## ステップ4: 基準時点の決定

各エージェントファイルの最終更新日を <PORTAL_REPO> の git log から取得する。

```bash
git log -1 --format=%ad --date=format:"%Y-%m-%d" -- .claude/agents/<agent>.md
```

## ステップ5: ディレクトリ構造の差分

基準時点のコミットと現在の `origin/<既定ブランチ>` で、深さ2までのディレクトリ集合を比較する。

```bash
git -C "$REPO" rev-list -1 --before="<基準日> 23:59" "origin/<既定ブランチ>"
```

追加・削除されたディレクトリを列挙する。

## ステップ6: パス参照の実在性照合

エージェント本文のバッククォート内文字列のうち、パスらしきものを抽出し、
`origin/<既定ブランチ>` のツリーに実在するか照合する。

**誤検出しやすいため、以下は照合対象から除外する。**

- `~/` `./` `../` `$` `@` `#` で始まるもの、URL
- 外部参照（`<GITHUB_ORG>/...`、`actions/checkout@v4`、`public.ecr.aws/...` 等のリポジトリ名・アクション名）
- 設定キー・HCL参照（`local.domains`、`var.`、`data.` 等）
- コード識別子（`child_process.exec` 等）
- tfstate のキー（`<product>/ec2-instance.tfstate` 等。S3上のキーでありリポジトリ内のパスではない）
- ブランチ名（`feature/...`）、バージョン番号、拡張子のみ（`.tf` 等）
- gitignore されうる設定ファイル（`.env.example`、`*.local.php` 等）

照合は**ベース名フォールバック**を併用する。ツリーに完全一致がなくても、同名のファイル・ディレクトリが
存在すれば一致とみなす（エージェントが `deploy-production.yml` のようにベース名だけで言及する記法を使うため）。

## ステップ7: 分類

検出結果を以下の3つに分類して提示する。**この分類が本手順の中核。**

| 分類 | 判断基準 | 例 |
|---|---|---|
| 実害あり | 現在存在しないものを案内している／コマンドが失敗する | 削除されたディレクトリを構成表に記載、パス設定のチルダ形式 |
| 追記推奨 | 新規コンポーネントが追加され、既存記述でカバーされていない | 新しいトップレベルディレクトリ（例: `e2e/`）の新設 |
| 対応不要 | 既存の汎用記述でカバーされている | `<function-name>/` と書いてある配下への関数追加、「resource_type 単位で分割」と書いてある配下への種別追加 |

**「差分がある＝要更新」ではない。** エージェントはカテゴリ単位で記述していることが多く、
その配下の増減は既存記述でカバーされる。個別列挙している箇所の乖離だけが実害になる。

## ステップ8: 適用（ユーザー承認後のみ）

1. 分類結果をユーザーに提示し、修正範囲の承認を得る
2. 作業用ブランチを作成する（`<DEFAULT_BRANCH>` を pull してから）
3. 編集する。複数箇所を機械的に置換する場合は、置換前に一致件数をアサートして
   意図しない箇所への波及を防ぐ
4. 波及確認を行う
   - `docs/ClaudeCode/agents-and-skills.md` のエージェント・スキル一覧との齟齬
   - `docs/ClaudeCode/getting-started.md` の記述との齟齬
   - `.claude/CLAUDE.md` / `README.md` への波及要否（<PORTAL_REPO> CLAUDE.md の規約）
   - 全エージェント・スキルの frontmatter 健全性（`name` / `description` の欠損がないか）
5. コミットし、PR を作成する。PR本文の先頭に `## 概要(ユーザー記入)` を空欄で設ける

## 厳守事項

- 対象リポジトリに対して `pull` / `checkout` / `commit` / `push` / ブランチ操作を行わない。`fetch` のみ
- `~/.claude/*-repo-path.txt` の書き換えはユーザー承認後に行う
- エージェント定義の編集はユーザー承認後に行う（<PORTAL_REPO> CLAUDE.md「確認なしに勝手にコードの作成・更新・削除をしない」）
- 対応不要と判断した差分も報告に含める。判断の根拠（どの汎用記述でカバーされるか）を明示する
